# Lab 04 — Services

## Objective
Understand a Kubernetes cluster's internal networking: how Pods
(ephemeral, with changing IPs) are exposed in a stable way through a
Service, and how internal DNS discovery works.

## Structure
```
lab-04-services/
├── README.md
└── manifests/
    ├── deployment.yaml          # 3 nginx replicas, backing the exposed Pods
    ├── service-clusterip.yaml   # Stable internal exposure (ClusterIP)
    ├── service-nodeport.yaml    # Exposure on every Node, fixed port (NodePort)
    └── client-pod.yaml          # Temporary busybox Pod to test DNS/curl
```

## What you create
- An nginx Deployment with 3 replicas
- A `ClusterIP` Service (`nginx-clusterip`) selecting the Pods via `app: nginx`
- A `NodePort` Service (`nginx-nodeport`) exposing the same Deployment on port `30080` of every Node
- A temporary client Pod (`dns-client`, busybox) to query internal DNS and curl the Services

## What you learn

| Concept | Explanation |
|---|---|
| ClusterIP | Default Service type, stable virtual IP, reachable only from inside the cluster |
| NodePort | Opens a fixed port (30000-32767) on **every** Node, forwards to the Service — reachable from outside the cluster |
| LoadBalancer | Provisions an external load balancer (cloud provider) ; not testable locally without a tool like MetalLB — theory only here |
| selector ↔ labels | A Service doesn't "know" Pods directly: it routes to any Pod whose labels match its `selector` |
| Endpoints | Resource automatically generated by Kubernetes, listing the IP:port of the Pods currently selected by the Service |
| Internal DNS | CoreDNS resolves `<service>.<namespace>.svc.cluster.local` to the Service's IP, re-evaluated on every Pod change |
| kube-proxy | Component on every Node implementing routing/basic load balancing to the Pods behind a Service (iptables/IPVS rules) |
| `kubectl port-forward` | Opens a local tunnel to a Pod or Service without going through NodePort/LoadBalancer — handy for ad-hoc debugging |

```bash
kind create cluster --name k8s-labs
```

## Steps

```bash
# 1. Deploy the 3 nginx replicas
kubectl apply -f manifests/deployment.yaml

# Check the Pods are running and grab their internal IPs
kubectl get pods -l app=nginx -o wide

# 2. Create the ClusterIP Service
kubectl apply -f manifests/service-clusterip.yaml

# Check the virtual IP assigned to the Service
kubectl get service nginx-clusterip

# Inspect the Endpoints: should list the 3 Pod IPs on port 80
kubectl get endpoints nginx-clusterip

# 3. Create the NodePort Service
kubectl apply -f manifests/service-nodeport.yaml

# Check the assigned NodePort (30080 here, set explicitly)
kubectl get service nginx-nodeport

# 4. Start the client Pod to test DNS resolution
kubectl apply -f manifests/client-pod.yaml

# Wait for the Pod to be ready
kubectl wait --for=condition=Ready pod/dns-client --timeout=60s

# Resolve the short DNS name of the ClusterIP Service (same namespace)
kubectl exec -it dns-client -- nslookup nginx-clusterip

# Resolve the full DNS name (FQDN)
kubectl exec -it dns-client -- nslookup nginx-clusterip.default.svc.cluster.local

# Curl the ClusterIP Service from inside the cluster
kubectl exec -it dns-client -- wget -qO- nginx-clusterip

# Repeat the curl a few times: notice the response may come from
# different Pods (load balancing done by kube-proxy)
kubectl exec -it dns-client -- sh -c "for i in 1 2 3 4; do wget -qO- nginx-clusterip | grep -o '<title>.*</title>'; done"

# 5. Access the ClusterIP Service from outside via port-forward
kubectl port-forward service/nginx-clusterip 8080:80
# In another terminal: curl http://localhost:8080
# Ctrl+C to stop the port-forward

# 6. Cleanup
kubectl delete -f manifests/client-pod.yaml
kubectl delete -f manifests/service-nodeport.yaml
kubectl delete -f manifests/service-clusterip.yaml
kubectl delete -f manifests/deployment.yaml

kind delete cluster --name k8s-labs
```

## Understanding checkpoints
- Why does a Service stay reachable even when a Pod restarts and gets a new IP? → The `selector` dynamically recomputes the `Endpoints`, while the Service itself keeps a stable virtual IP.
- What happens if no Pod matches a Service's `selector`? → The Service still exists (IP allocated) but its `Endpoints` are empty; any request fails (connection refused or timeout).
- Why isn't NodePort the recommended way to publicly expose an app in production? → Limited port range (30000-32767), no native domain name or TLS, a single Node is enough to reach the Service but it isn't designed for large-scale public traffic (that's the role of an Ingress, covered in Phase 3).
- Difference between `port` and `targetPort` in a Service? → `port` is the port exposed by the Service, `targetPort` is the port actually listened to by the container in the Pod; they can differ.
