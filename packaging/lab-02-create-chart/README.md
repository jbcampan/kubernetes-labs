# Lab 02 — Create Chart

## Objective

Create a Helm chart from scratch (`helm create`), repackaging a Deployment +
Service already known from Phase 1, in order to understand the internal
structure of a chart and the underlying Go templating mechanism.

## Structure

```
lab-02-create-chart/
├── README.md
└── helm/
    └── nginx-app/
        ├── Chart.yaml              # Chart metadata (name, version, appVersion)
        ├── values.yaml             # Default values injected into templates
        ├── .helmignore              # Files ignored when packaging (helm package)
        └── templates/
            ├── _helpers.tpl         # Named templates (common labels, fullname...)
            ├── deployment.yaml      # Templated Deployment
            ├── service.yaml         # Templated Service
            └── NOTES.txt            # Message shown after a helm install/upgrade
```

## What you create

- A complete, functional Helm chart (`nginx-app`), structured like what
  `helm create` generates, but cleaned of unnecessary files (no
  ServiceAccount, Ingress, or HPA — out of scope for this lab)
- A `_helpers.tpl` with common labels and selectors reused everywhere
- A `values.yaml` that fully drives the number of replicas, the image, and
  the Service type, without touching the templates

## What you learn

| Concept | Explanation |
|---|---|
| Mandatory chart structure | `Chart.yaml` (metadata), `values.yaml` (default config), `templates/` (templated manifests) — without these three, `helm lint` fails |
| Go templating syntax | `{{ }}` delimits an evaluated expression; `.Values.x` reads `values.yaml`; `{{- ... -}}` strips whitespace/newlines around the block |
| Helm built-in objects | `.Release.Name` (name given to the install), `.Release.Namespace`, `.Chart.Name`/`.Chart.Version`/`.Chart.AppVersion` — available in every template without declaration |
| `_helpers.tpl` and named templates | `define "name"` declares a reusable block, `include "name" .` invokes it while passing the context (`.`) — avoids duplicating labels across manifests |
| `nindent` | Sprig function that re-indents a multi-line block at the right YAML level before inserting it (essential so the labels generated by `_helpers.tpl` line up correctly) |
| `helm lint` | Validates the chart structure and template syntax without deploying anything |
| `helm install --dry-run --debug` | Renders the templates with real values and prints the final YAML, without touching the cluster — the reflex before every `helm install` |

## Estimated cost

€0 — local kind cluster, public `nginx` image, no AWS resources.

## Prerequisites

```bash
kind create cluster --name k8s-labs
kubectl cluster-info --context kind-k8s-labs
```

## Steps

```bash
# 1. Move into the lab folder
cd packaging/lab-02-create-chart

# 2. Validate the chart structure and template syntax
helm lint ./helm/nginx-app
# → should print "1 chart(s) linted, 0 chart(s) failed"

# 3. Render the templates without deploying, to check the generated YAML
helm install nginx-demo ./helm/nginx-app --dry-run --debug
# → inspect the output: generated names (nginx-demo-nginx-app),
#   injected labels, values.yaml correctly substituted

# 4. Actually install the chart
helm install nginx-demo ./helm/nginx-app

# 5. Check the release and the created resources
helm status nginx-demo
kubectl get all -l app.kubernetes.io/instance=nginx-demo

# 6. Test access to the Service
kubectl port-forward svc/nginx-demo-nginx-app 8080:80 &
curl http://localhost:8080
kill %1

# 7. Change a default value without touching the templates
helm upgrade nginx-demo ./helm/nginx-app --set replicaCount=3
kubectl get pods -l app.kubernetes.io/instance=nginx-demo
# → 3 Pods instead of 2, no YAML file modified

# 8. Uninstall the release
helm uninstall nginx-demo

# 9. Clean up the cluster
kind delete cluster --name k8s-labs
```

## Understanding checkpoints

- **`.Release.Name` vs `.Chart.Name`**: `.Release.Name` is the name given
  *at install time* (`nginx-demo` in the commands above, freely chosen at
  each `helm install`); `.Chart.Name` is the name *of the chart itself*
  (`nginx-app`, fixed, defined in `Chart.yaml`). That's why the final
  resource names combine both (`nginx-demo-nginx-app`) — the same chart
  can be installed multiple times in the same cluster under different
  release names, without collision.
- **`version` vs `appVersion`** in `Chart.yaml`: `version` follows the
  lifecycle of the *chart* itself (its templates, its structure);
  `appVersion` is purely informational and indicates which version of the
  application (nginx here) the chart deploys by default — Helm never uses
  it for templating logic.
- **Why `_helpers.tpl` instead of copy-pasting labels**: in this 2-resource
  lab the benefit is still limited, but as soon as a chart grows (Ingress,
  ConfigMap, HPA...), duplicating the same 4-5 labels in every file becomes
  a source of inconsistencies. `include` centralizes the definition in one
  place.
- **Difference from the raw manifests in Phase 1**: functionally the same
  Deployment and Service, but here no value is hardcoded — changing the
  replica count or the image version is done via `--set` or a custom
  `values.yaml` file, without ever editing the templates.
